## Spec

**§1 Problem statement**  `SPEC §1`
> You are giving a lot of new rules. This is good. But let's think in the next time we pass a process like this: arsenal should have a way (a new skill?) to do this automatically. I mean, if some day Claude 6 is released, we'll need to make a review like this, taking into account similar things, from reading newest docs to do some checks like the ones you just proposed. I'd like to have a stricter method to do this (a meta-meta-tool).
> Also, workshop-skill must always be at the center of each model update, since it is part of validation and verification.
> I'm sure reducing tokens will always be a requisite (maybe in the future not so much, like with computer memory, but let's keep it shorter when possible) so while keeping all new rules, let's try to reduce it always. Shorter outputs are also desired. Oh, and one thing I always find: arsenal names tasks by their I'd, but I don't know those IDs and the text around them is hard to understand to me. Let's try to give a very short title to each task, so I can understand better what they are actually doing, and show that text in your outputs or questions.

**§2 Systems & Impact**  `SPEC §2`
> About linked MD files in skill files, check what Anthropic proposes to make them useful. Give them a review thinking how they are used. I mean, if after reading a skill, a reference document is ALWAYS read, maybe it should be in the skill file and if it was split by size, maybe we must reduce skill size. This should be taken into account in skill-workshop.
> Our initial skill-workshop research must be obsolete right now. We'll need to keep it updated somehow. Keep the old version, but add new findings somewhere.
> About adversarial reviews, we had a lot of issues with them in last weeks. PRs never finish to merge because our tests, checks an so take too much time. I have seen 8 reviews of 40 minutes each for just one PR. We need to improve that. Sometimes we have GitHub CI (or similar) and bot reviews like CodeRabbit (or similar) enabled. In case they don't work (payment or hourly limits, for example), then we must use our own adversarial checks, but running full tests on each commit or similar can make it too long. We must find a balance for the code correctness and time taken. The system must be able to detect existing tools (for example, CodeRabbit won't AUTOMATICALLY work for repos with less than 10 stars, but they will work anyway if asked unless hourly limit is reached) and decide what to do and how to reduce checking times without losing confidence. Verification in launched agents must be coherent with the session and the repo wide rules to not make things eternal. This is very important and must be solved now.

**Option B: Codify, enforce, then rewrite in tiers (Recommended)**  `SPEC › Option B: Codify, enforce, then rewrite in tiers (Recommended)`
> Maybe we'll need some more configuration items: how much the model asks the user, level of confidence... I don't know, but we also need some configuration by the user at the beginning in some kind of interview.
> We were working on something for after compaction, I don't know if it already landed.
> Can you automatically change your model or effort depending on the needs?

**§4 Recommendation**  `SPEC §4`
> I think I prefer C. Let's fix how adversarial reviews work as I explained above, keep the canary lines (a hook won't hurt) and boom to 5.0.0.
