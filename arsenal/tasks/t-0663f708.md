title: "tag-release.yml publishes a tag regardless of whether CI passed"
priority: 10
tags: [ci, release]
---

tag-release.yml fires on any push to main and creates v<.bundle-version>. It has
no `needs:`, no `workflow_run:` trigger, and no check of ci.yml's conclusion —
confirmed by reading the whole file.

Failure scenario: a merge to main whose fresh main-branch CI run goes red is
still tagged. Every consumer's check_update.sh gates on exactly the newest
remote tag, so that red release becomes the version they are offered and
subtree-merge into their repo.

The workflow reasons carefully about the opposite failure — a release shipping
UNTAGGED when Actions is unavailable — and added a daily cron to self-heal it.
Nothing guards the tagged-despite-red direction.

Done means: a tag is published only for a commit whose CI concluded successfully,
without losing the outage-recovery path the cron provides.
