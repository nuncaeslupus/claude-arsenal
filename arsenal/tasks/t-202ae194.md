Two defects in dependency handling, one dangerous and one merely silent.

1. load_tasks keeps deps only `if isinstance(deps, list) else []` (:469), while
   requires and tags both go through _as_list (:415-427) — whose own docstring
   documents this exact bug class for requires. So `deps: t-a1b2c3d4` written
   bare, without brackets, parses to a string and becomes []. The task is then
   offered as UNBLOCKED and runs before its prerequisite. The sibling bug fails
   safe (a task will not match); this one fails dangerous.

2. select() treats any dep whose state is not in TERMINAL={done,merged} as
   blocking, so a dep cancelled via `arsenal:cancelled` blocks its dependent
   forever — with none of the diagnostics the other blocking paths emit (an
   unknown dep warns at :508-512; a capability or workspace mismatch warns).
   The task simply stops appearing, with no explanation anywhere.

Done means: a bare deps scalar is normalised like requires and tags, and a
dependent blocked by a cancelled dep says so.


## Acceptance gate

```bash
python3 - <<'PY'
import sys, tempfile, pathlib
sys.path.insert(0, "plugins/core/skills/init/assets/scripts")
import task_select
d = pathlib.Path(tempfile.mkdtemp())
(d / "t-aaaa1111.md").write_text("---\nid: t-aaaa1111\ntitle: dep\n---\n")
(d / "t-bbbb2222.md").write_text("---\nid: t-bbbb2222\ntitle: dependent\ndeps: t-aaaa1111\n---\n")
tasks, _ = task_select.load_tasks(d)
dep = next(t for t in tasks if t["id"] == "t-bbbb2222")
assert dep["deps"] == ["t-aaaa1111"], f"bare deps dropped: {dep['deps']!r}"
PY
```
