▸Technical solution

▸Architecture overview

The module layout is spec § 5.1. Three layers, built bottom-up so each PR has a tested substrate under it:

  1. Substrate (P1) — _brlib.py resolves the input (txt / zip / UTF-16, § 5.2), scans delimiters into name#occurrence sections (§ 5.4), and keeps a byte-offset index in the per-user cache (§ 5.3). _redact.py filters every emitted string (§ 5.10). query_bugreport.py and validate_bugreport.py sit directly on it, so the fallback route ("not parsed → locate, sample") exists before any detector does.
  2. Detectors (P2, P3, P4) — _detectors.py owns the registry, Finding, NotParsed and the fail-soft run loop (§ 5.8); one _det_<slug>.py per family. analyze_bugreport.py is the run loop plus ranking and the bugreport.analyze/1 envelope (§ 5.6).
  3. Interpretation and sharing (P4) — references/advice.md (§ 5.9), create_bugreport.py --redact, compare_bugreport.py.

har is the precedent for shape (two-layer tests, output budget, redaction stance) and is not imported (§ 5.1).

▸Data flow

--input → open_report (key from size + mtime + head/tail hash) → cache hit: load index.json; miss: stream-scan (and, for zip/UTF-16, write main.txt) → Report. Commands then read only slices (seek(start), verify delimiter, read size bytes) or named FS/ members. Detectors turn slices into Findings; the run loop ranks, applies the byte budget, redacts, and prints one JSON document.

▸Technology choices

Choice Justification
stdlib only (mmap, re, zipfile, zlib, json, hashlib, hmac, zoneinfo) Spec criterion: zero third-party runtime deps; the core tests job runs bare python3
Byte-offset JSON index, not SQLite Spec Option B tradeoff: one file, no conversion step; timeline can grow a SQLite backend later behind the same interface
Extract the zip main entry once (not stream per query) § 5.2: deflate has no random access; per-query re-decompression breaks query_s <= 1
Hand-rolled protobuf wire reader ~100 lines for varint + length-delimited; avoids a protobuf dependency (spec criterion)
pytest unit layer + bash CLI layer The har split: scanner/clock/redaction are unit problems; bugreport_test.sh asserts exit codes and budgets the way a session calls the scripts

▸Out of scope

Perfetto integration (D-3), MCP wrapper (D-2), live adb capture, logcat-only or ANR-only inputs (room left in the android section), comparison analytics beyond the JSON diff (D-7), a SQLite logcat backend, and committing any real report or excerpt (D-9).

▸Merge order and PRs

PR Tasks Branch Bump

Stacked from the start, per github references/stacking.md: only P4 bumps .bundle-version and adds the CHANGELOG.md entry, so the release has one bump commit and consumers see one coherent "new bugreport skill" entry rather than three half-skills. Inside P2–P4 the tasks run in table order; T11–T13 and T15–T19 are independent of each other and may be parallel commits.

This collides with CI's version bump job, which requires a bump on any PR whose diff against its base touches plugins/*/skills/ — true of P1–P3. Designs 0002 and 0004 resolved the same collision by bumping every PR. To keep the stacking rule, this plan merges the stack top-down into P1's branch: P4 → P3 → P2 → P1 (each approved on its own diff), then P1 → main as one squash carrying the bump. CI (.github/workflows/ci.yml) runs only on pushes to main and PRs into main, so P2–P4, which target stacked branches, get no CI at all: their gate is make test plus the task gates run locally on each branch head, with the output recorded in the PR body, and the adversarial review. The first CI run over T10–T24 is the P1 → main PR after the stack is folded in, which is the real merge gate. Chosen by the maintainer (spec D-10): one bump, top-down merge.

P1 alone is useful: query + validate are the spec's Option A coverage (sections map, traps, cheap fallback) — but under top-down merging nothing ships until P4 lands, so a stall after P1 means merging P1 to main with its own bump.

After the release merges: make release-check; on NO TAG, ask the maintainer to run make tag from their machine (CLAUDE.md § Versioning).

▸Fixtures — generated, never captured

Every fixture is built at test time by make_fixture.py (§ 5.11); only seeds are committed. One scenario per detector branch, so a failure names its cause:

Before the release (T24), the maintainer's five Pixel reports and the public corpus are re-run locally with the zero-error: bar and the provenance diagnosis and the T25 summary coverage windows (within one minute of the hand-read values) checked by hand (D-9); the result is recorded in the Evidence log as Env: local, beside — never instead of — the CI rows.

▸Evidence log

execution appends one row per task as it lands (RED → GREEN → RECORD): the measured value, the exact command that produced it, the commit SHA, and the environment provenance. review / ship audit this table; gate-check's run_gate.py reads it. A gated task is not "done" until its row is complete and the measured value meets the gate.
