Why this exists. An Android bugreport already holds the full answer to "why did my phone freeze / drain / reboot / kill my app": logs, event tags, memory and process stats, ANR traces, tombstones, battery history. It is also a 100–250 MB text file with 800+ sections in a dozen formats, so the one thing nobody can do with it is read it. This document specifies a script set that turns it into a short, evidenced list of findings — the same move the har skill (design 0002) made for browser captures.

§1Problem statement

Diagnosing a bugreport today means grepping a huge flat file by hand, learning each section's ad-hoc format on the way, and re-deriving the same parsers every time. The provenance case: one real Pixel bugreport (Android 16, 156 MB text, 234 MB zip) asked "what happened?" took a session ~15 tool calls to reach a diagnosis that is fully deterministic — memory thrashing (swap 97 % full, kswapd 58 % CPU, I/O PSI some avg10=89) causing two input-dispatch ANRs — and two of those calls were lost to format traps (embedded \r bytes shifting line numbers; locale decimal commas 1,9GB in procstats). The tools that used to interpret bugreports are gone: Battery Historian (archived 2022, battery only) and ChkBugReport (archived 2026, pre-2016 parsers). Perfetto ingests a bugreport zip but stores dumpstate as raw lines and interprets nothing. No official or community Claude skill analyses offline bugreports (Google's android/skills covers Perfetto traces only). Forum demand is dominated by battery drain, then overheating, random reboots, and lag/ANR/crashes — all of which a bugreport answers if something reads it.

The goal: a session (or a human at a terminal) gets a ranked, evidenced diagnosis from one command, and every follow-up question costs one more command whose output is a few hundred bytes — never a section pasted into context.

▸Requirements (from the maintainer)

  1. Scripts, not reading. Ultra-fast deterministic scripts return only the result; the session judges, it never pays tokens for the search.
  2. Find problems, not just expose data. A detector catalogue turns raw sections into findings with severity and evidence.
  3. Helps more people than its author. End users (battery, heat, freezes, reboots) and app developers (ANR root cause, native crashes, why the app is killed) are both first-class.
  4. Efficient reading. Decide, with measurements, whether to index or convert the file rather than re-scanning it per question.
  5. Lives in arsenal as a tool, alongside har, following its conventions.
  6. An auto-diagnostic, not a parser. "How is my phone doing?" runs every detector and answers with problems and remedies (close or restrict an app, cut battery use, avoid heat, free storage…), including problems the user has not noticed yet.
  7. Security and hygiene are in scope: apps installed outside an app store, risky permissions and app configurations, device-level security settings.
  8. Nothing is unreachable. When a section cannot be parsed (a new Android release, an OEM format), cheap generic primitives still let the session locate, sample and interpret it without reading it whole.
  9. Built to skill-workshop rules (§ 2.4) — the rubric gates every file in the skill folder.
  10. No Perfetto dependency; its ideas may be borrowed.
  11. Broad coverage: test material from several Android versions and OEMs, not only the maintainer's phone.
  12. A summary of the file — device model and OEM, Android build and patch level, which time span each data source covers, and basic statistics — so the first question "what is in here?" costs one command.

Success criteria (measurable)

  • [ ] index_build_s <= 3 for a 160 MB bugreport text on the CI runner (measured today: one mmap + regex pass over 156 MB finds 842 sections in 0.96 s); peak_rss_mb <= 300.
  • [ ] query_s <= 1 for any single-section command once the index exists (seek to byte range, parse only that slice).
  • [ ] checkup_output_bytes <= 4096 by default, enforced by truncation; every finding carries an evidence pointer (section + byte offset or file path) so the full text is one show command away.
  • [ ] commands_to_diagnosis <= 1: analyze_bugreport.py (full checkup) on the provenance bugreport reports memory thrashing as the top finding, names the ANR'd processes as victims, and lists the top memory holders — judged against the manual diagnosis recorded above. In CI this runs on a synthetic fixture reproducing that report's signals (swap ≥ 95 %, kswapd CPU, PSI, two input ANRs); the real report is re-checked locally before release (D-9).
  • [ ] Detector coverage: each problem family F1–F11 in § 2.2 has ≥ 1 detector with a fixture that fires it and one that does not (make test asserts both).
  • [ ] Advice coverage: every finding id has an entry in references/advice.md (a test diffs the two id sets; missing entry = build failure).
  • [ ] Android version / OEM coverage: synthetic fixtures reproduce the layouts seen in the corpus (§ 2.1.1) — pre-P (no priority blocks), 9–17 with CRITICAL/HIGH, Samsung DUMPSYS NORMAL + OEM sections, Xiaomi/OnePlus/Huawei sections, zips without main_entry.txt — and all parse in CI with zero unhandled exceptions; before each release the real corpus is re-run locally (not in CI) with the same zero-exception bar. Unknown sections degrade to "not parsed", never a crash.
  • [ ] summary_output_bytes <= 2048 and every summary field present (value or unknown) on every layout fixture; on the provenance report the coverage windows match the hand-read values within one minute.
  • [ ] Fallback cost: for a section with no parser, commands_to_first_fields <= 2 (query … locate, then query … sample), each output_bytes <= 2048.
  • [ ] validate_skill.py (skill-workshop) reports 0 must findings on the skill folder.
  • [ ] pii_in_default_output == 0: emails, IMEI/IMSI/ICCID, phone numbers, MAC addresses and SSIDs never appear in default output (asserted by a test over a seeded fixture); --no-redact is the explicit opt-out.
  • [ ] Zero third-party runtime dependencies for the core scripts (stdlib only, uv run python), including tombstone .pb decoding.
  • [ ] Resident listing cost <= 130 tokens for installs with the skill's section enabled and 0 for installs without it (make context-budget).

§2Systems & Impact

§2.1What a bugreport contains (parser facts)

  • Zip layout: main_entry.txt names the main text (bugreport-<build>-<date>.txt); version.txt gives the format (2.0 since Android P); FS/ mirrors device paths — FS/data/anr/ (ANR traces, one file per ANR), FS/data/tombstones/tombstone_NN + .pb (native crashes; protobuf since Android 12), FS/data/misc/logd/ (persistent logcat, when enabled), FS/data/misc/recovery/ and update_engine_log/ (OTA); proto/*.proto (binary dumps of some services, build-dependent — 12 files in the provenance report); dumpstate_board.txt (vendor HAL); visible_windows.zip.
  • Delimiters: ------ SECTION TITLE (command) ------ for top-level sections, DUMP OF SERVICE [CRITICAL|HIGH ]<name>: inside the three DUMPSYS priority blocks (a service can appear more than once), ------ 0.123s was the duration of 'SECTION TITLE' ------ closers, *** command '…' timed out for truncated sections.
  • Where the size is (provenance report): Wi-Fi HAL dump 16.5 MB, CHECKIN BATTERYSTATS 15.3 MB, batterystats 11.2 MB, activity 9.3 MB, package 7.4 MB, VM traces 5.9 MB, system log 5.1 MB. Logcat is not the bulk; a section index makes almost every question a slice read.
  • Traps (each one has already cost a real session a step): bare \r bytes inside lines (10 757 in the provenance file — text-mode readers shift line numbers); locale-formatted numbers (0,00, 1,9GB); UTF-16 text when a .txt was captured through PowerShell redirection; NUL/invalid UTF-8 in logcat; logcat in local time vs batterystats/kernel in UTC/elapsed (offset from the alarm dump's nowRTC/nowELAPSED, as Perfetto does, or persist.sys.timezone); procstats PSS triples reading 0,00 when unsampled (use RSS as fallback).

Pick the largest text entry with a dumpstate header.

§2.4Skill-workshop constraints the design must meet

  • Authoring runs under /skill-workshop:skill-workshop; its validator must report 0 must findings.
  • Frontmatter: name: bugreport (folder name, kebab-case), third-person description stating what + when with a negative trigger ("Not for live-device adb sessions or logcat-only files" — or whatever scope v1 ends with), no angle brackets, metadata.section: android, metadata.type: tool, allowed-tools pre-approving the script invocations.
  • Body ≤ 500 lines, imperative voice, no second person; standing constraints (privacy, output cap, fallback route) front-loaded; detail in references/ with "load when…" triggers; references/_index.md if the body passes 300 lines; each reference ≤ 10K tokens; no PII in references.
  • Scripts: verb_noun.py naming, canonical flags (--input, --output, --output-dir, --json, --limit, --since), domain flags --family, --advice, --no-redact, --window registered in the validator's canon list rather than invented ad hoc, stdout = payload only, progress and errors on stderr via _console.py, exit codes 0/1/2, main() + guard, no top-level work, --help on every script.
  • Evals: loading-verification + trigger evals in evals/, like har.

Impact summary: Data — read-only on the input, sidecar index in --output-dir (default: a per-user cache dir keyed by the input hash, so read-only inputs and zips work); API — new CLI surface, no existing contract changes; Performance — bounded by the criteria above; User — opt-in skill; Operational — fixtures must never contain a real report; Risk of inaction — every bugreport question keeps costing ~15 calls and re-learned traps.

§3Options

▸Option A: Recipe reference + a handful of grep scripts (Conservative)

  • Description: A SKILL.md plus a references/sections.md cheat-sheet of section names, patterns and traps, and 3–4 small scripts (summary, anr, memory) that each scan the whole file.
  • Scope: New skill folder only.
  • Effort: Small
  • Tradeoffs: Fast to ship and already cuts most wasted calls. No problem detection — the session still diagnoses; each script re-scans the file (~1 s each, fine); format knowledge is spread across scripts and drifts.
  • Compatibility: Additive.

▸Option B: Indexed, detector-driven toolkit, stdlib only (Recommended)

  • Description — five scripts sharing one library (_brlib.py: index, slice reader, tolerant number parsing, redaction filter, _console.py):
    • analyze_bugreport.py — the entry point. Builds or reuses the index, then runs detectors and emits findings. Default mode is the full checkup (all families F1–F11); --family memory,anr,… narrows it. Each finding: id, severity, family, one-line claim, key facts (numbers), evidence pointer (section + byte offset, or FS/ path), advice_id. Family views give the fixed compact tables a follow-up needs: memory (procstats 24 h memory × time by process and state, meminfo, swap, PSI, lmkd kills), ANR (reason, victim vs pressure, main-thread state, top CPU), crashes (tombstones via a ~100-line stdlib protobuf varint decoder, Java fatal exceptions, exit-info reasons), battery (from the checkin CSV, not the text form), reboots, thermal, churn (kill → restart loops and what restarted them), security & hygiene.
    • query_bugreport.py — generic primitives, so a section with no parser (new Android release, OEM format) is still cheap to interpret: sections (stable id name#occurrence — a service dumped in several priority blocks gets #1, #2… in file order — plus service, size, parse status; every other command takes that id), locate --grep RE (hit counts per section, no lines), sample SECTION (first lines, plus a format sniff — key=value, table, indented tree, CSV — and the shape of its repeated records), show SECTION --grep RE --context N --limit N, timeline --since HH:MM --window 5m (event log + system log + ANR/kill markers merged). All output capped; full text goes to --output FILE.
    • validate_bugreport.py — is the input a bugreport, which format version, Android version, OEM, encoding fixed, which detector inputs parsed and which fell back. A falling-back detector names the query command to use instead, so drift shows up as a route, not a silent gap.
    • create_bugreport.py --redact — writes a scrubbed copy for sharing (emails, IMEI/MEID by Luhn, IMSI and ICCID by prefix + length, phone numbers, MACs, SSIDs, account names, coordinates); the same filter is on by default for all stdout.
  • Advice split (D-6): scripts stay deterministic and only emit advice_id plus the facts; references/advice.md maps each id to a remedy template (what to do, Settings path per Android version, when to escalate to repair/support), loaded only when advice is needed; the session phrases it for the user's situation. --advice adds the one-line canned remedy to each finding for terminal use.
  • Comparison (D-7): no analysis of its own. analyze --json has a versioned, stable schema, so "before vs after" means running it on two reports; compare_bugreport.py is a small diff of two such JSON files (new / gone / changed findings, memory and battery ranking deltas), last in the plan and droppable.
  • Ideas borrowed from Perfetto, no dependency: the section/service two-level model, the logcat-local vs UTC offset taken from the alarm dump's nowRTC/nowELAPSED, scanning FS/ for embedded traces and logs.
  • Output discipline from har and skill-workshop: compact JSON on stdout ≤ 4096 bytes by default (when capped, the payload stays valid JSON: {"truncated": true, "omitted": N, …} envelope, asserted by a test that parses every capped output), progress on stderr, --output for full fidelity, --help everywhere.
  • Scope: New skill folder, section entry, tests + synthetic fixtures, changelog.
  • Effort: Large (4 stacked PRs: P1 library + index + query + validate + fixture generator; P2 memory/ANR/churn/thermal detectors + checkup; P3 crashes/battery/reboots/network/Bluetooth/storage/battery-health; P4 security & hygiene + advice reference + redaction + compare).
  • Tradeoffs: The detectors are the value and also the maintenance cost: formats shift between Android releases and OEMs, so every detector must fail soft ("section not parsed") and be fixture-tested. Byte-range index over SQLite: one JSON file, no conversion step; SQLite only earns its keep for repeated time-window logcat queries, which timeline can add later behind the same interface.
  • Compatibility: Additive; no dependency on Perfetto or protobuf libraries.

▸Option C: Build on Perfetto trace_processor as the substrate (rejected by the maintainer — ideas only)

  • Description: Load the zip into Perfetto's SQL tables (android_logs, android_dumpstate, battery_stats) and write the detectors as SQL queries over them.
  • Scope: New skill + a pip dependency (perfetto) that downloads a native binary.
  • Effort: Medium
  • Tradeoffs: Free logcat parsing and SQL joins, and alignment with Google's own trace skill. But dumpstate is stored as raw lines (detectors still parse text, now inside SQL), batterystats import is partial (~30–40 % of events per Perfetto issue #934), load time and RAM are far above a byte-range index, and the binary download fails in network-restricted environments (cloud sessions, CI behind proxies).
  • Compatibility: Additive, but adds a heavy runtime dependency to a stdlib-only bundle.

▸Option D: MCP server instead of a skill

  • Description: Expose the same analyses as MCP tools.
  • Tradeoffs: MCP earns its place for remote systems, auth, live state or non-Claude clients. For a local file it adds a server process and up-front tool-definition tokens while doing exactly what uv run python script.py already does; the skill's resident cost is one listing line, and script output is already bounded before it reaches context. Google's Perfetto skill made the same call (bundled CLI, not MCP). A thin MCP wrapper over Option B's CLI stays possible later if non-Claude agents need it; live device capture over adb is already covered by existing MCP servers.
  • Effort / Compatibility: Medium; separate install path outside the marketplace model.

§4Recommendation

Recommended option: B — it is the only option that meets "find problems, not just expose data" without a native dependency, and it reuses the decisions har already proved (index sidecar, bounded output, redaction by default, --json escape hatch). A's scope (a sections reference plus grep-level access) is covered by B's P1 (query + validate); C stays an optional backend idea for logcat-heavy questions; D is rejected for v1.

Immediate next action: after approval, run design to turn this into contracts and a stacked PR plan; first PR = P1 (library, index, query, validate, synthetic-fixture generator), so every later detector has a fast, tested substrate and the fallback route exists from day one.

Gates check: objective (§ 1), scope (§ 2.3), impacted systems (§ 2.3), compatibility (additive, minor bump), risk (format drift, PII — § 2.1/§ 2.3), validation (success criteria), release readiness (changelog entry + make context-budget row).

Open questions: none — all resolved in the decisions log.

Decisions log: - D-1 — Lives inside claude-arsenal (not a separate repo), as a tool skill like har (maintainer, 2026-11-04). - D-2 — Skill + stdlib scripts, not an MCP server (this spec, Option D rationale; open to a thin MCP wrapper later). - D-3 — Option B approved; Perfetto not used, ideas may be borrowed (maintainer, r2 notes). - D-4 — Section android, default-off, skill folder under plugins/core/skills/ like every vendored skill (maintainer: "an Android section or inside diagnostics"; android chosen as the narrower, self-describing name). - D-5 — Full checkup with remedies, security & hygiene in scope, all families F1–F11 in v1 (maintainer, r2 notes). - D-6 — Advice: deterministic advice_id from scripts, remedy text in a reference the session interprets (maintainer: "a part of it could be from the skill for the LLM to interpret"). - D-7 — No comparison analysis; stable JSON plus a small compare_bugreport.py diff, last and droppable (maintainer, r2 notes). - D-8 — Built and validated under skill-workshop rules (maintainer, r2 notes). - D-9 — Real reports (public corpus and the maintainer's own) are study material only: they inform which data to read and keep, how to preserve privacy, and which concrete cases detectors must catch. They are never committed, not even as excerpts. CI runs on synthetic fixtures built from what the real reports taught (maintainer, 2026-11-04).

§5Contracts

Sections 5–6 are appended by design (2026-11-04). They settle the items the spec's reviewers left for design — the index/cache, zip input, the clock behind timeline --since, the output schema, the CLI surface, detectors, advice, redaction and the fixture generator — so the plan (0005-bugreport-analysis-toolkit-plan.md) can gate each task against a written contract, not against intent. Nothing here changes §§ 1–4.

§5.2Input resolution

--input takes a .txt or a .zip. Detection is by content (zip magic PK\x03\x04), not extension.

Text input. Read in binary mode throughout — never text mode, which is what shifts line numbers at bare \r bytes. Encoding is sniffed from the first 4 KiB: a UTF-16 BOM (or ≥ 30 % NUL bytes in even/odd positions without one) means UTF-16 and the file is transcoded once into the cache as UTF-8 (§ 5.3); otherwise the input is used in place via mmap. Invalid UTF-8 and NUL bytes inside logcat are decoded errors="replace" per slice, never fatal.

Zip input — finding the main entry, in order:

  1. main_entry.txt exists and names a member that exists → that member.
  2. Otherwise, every .txt member outside FS/ and proto/, other than version.txt, main_entry.txt, dumpstate_board.txt and dumpstate_log.txt, whose first 64 KiB holds a dumpstate header (^== dumpstate: \d{4}-\d{2}-\d{2} or ^Bugreport format version:) → the largest of them. This covers dumpstate-<date>.txt, dumpstate.txt and arbitrary names (example.txt).
  3. None → exit 1, listing up to five largest text members, so the session can point --input at one by hand.

Streaming vs extracting. The main entry is extracted once into the cache, streamed in 1 MiB chunks through the same scanner that builds the index (one decompression pass; never held whole in memory). Deflate has no random access, so a streaming-only design would re-decompress up to a section's offset on every show — ~0.5 s per 100 MB, which breaks query_s <= 1 for sections near the end of a 156 MB entry. The cost is disk: the cache holds a copy the size of the main entry. FS/ members (ANR traces, tombstones, .pb, persistent logd, recovery logs) are not extracted; they are read on demand by member name, streamed, since each is small or read once.

Build-time criterion covering the zip. Alongside the spec's text criterion (index_build_s <= 3, peak_rss_mb <= 300 for 160 MB text), the zip path is gated as index_build_zip_s <= 6 and peak_rss_mb <= 300 for a 234 MB zip whose main entry is 156 MB (extract + scan, cold cache), and index_reuse_s <= 0.5 for any later command on the same input (warm cache). Both are measured on the CI runner against a generated report of that shape (§ 5.11, scale mode).

§5.3Index and cache

Location. Unlike har, which writes <file>.har.index.jsonl beside its input, this skill never writes beside the input: bugreports often sit on read-only media or in a download folder, a zip has nowhere sensible to put a sidecar, and the extracted main entry is a full-PII copy that must not land in a working tree where it can be committed. The default root is the standard per-user cache directory:

Platform Default root
Linux / BSD $XDG_CACHE_HOME/claude-arsenal/bugreport/, else ~/.cache/claude-arsenal/bugreport/
macOS ~/Library/Caches/claude-arsenal/bugreport/
Windows %LOCALAPPDATA%\claude-arsenal\bugreport\Cache\

--output-dir DIR always overrides the root (the cache lands at DIR/<key>/). Directories are created 0700, files 0600. Each input gets <root>/<key>/ holding index.json and, for zip or UTF-16 input, main.txt. Builds write to a temp file in the same directory and os.replace it, so an interrupted build leaves the previous index intact. On each build the root is pruned to the five most recently used keys (a module constant, stated as a starting value); the cache is otherwise disposable and documented as such.

Key. key = sha256(f"{size}:{mtime_ns}:" + sha256(first 1 MiB ‖ last 1 MiB))[:16] — about 3 ms on a 160 MB file, against ~1 s for a full hash. Stale-index trade-off: an in-place edit that keeps size and mtime and touches only the middle of the file is not detected by the key. Bugreports are not edited in place, so the residual case is deliberate tampering; it is covered cheaply by a delimiter check on every slice read — the bytes at a section's start must be that section's opening line (------ TITLE or DUMP OF SERVICE …). A mismatch rebuilds the index once, then fails with exit 1 if it recurs. --force rebuilds unconditionally.

Contents — offsets and metadata only, never section text (asserted by a test that greps every index.json for each fixture's canary strings):

§5.4Section ids and selectors

  • A section's name is the title between ------ and ( for top-level sections (SYSTEM LOG, KERNEL LOG (dmesg) keeps its own parentheses — the scanner splits on the last ( before ------), and the service name for DUMP OF SERVICE blocks (meminfo, batterystats).
  • id = name#occurrence, occurrence 1-based in file order. Every id carries its occurrence (meminfo#1), so ids are stable across runs on the same file.
  • --section accepts an exact id; a bare name when it has exactly one occurrence; and a case-insensitive match when that is unique. Anything ambiguous is exit 2 with the candidate ids on stderr — never a silent pick.
  • Ids are not stable across reports (a service can gain a priority block between releases), which is why compare_bugreport.py never keys on them (§ 5.7).

§5.5Clock and timeline --since

Clock domain: device local wall-clock time. Every timestamp the scripts emit is normalised to YYYY-MM-DD HH:MM:SS.mmm in device local time, because that is what logcat prints and what the user remembers ("it froze at about 14:15").

Source Native form Conversion to local
logcat (SYSTEM, EVENT, RADIO, LAST LOGCAT, FS/…/logd) MM-DD HH:MM:SS.mmm, local, no year Year from captured_local; a month later than the capture month belongs to the previous year (December logs in a January report)
ANR trace files ----- pid N at YYYY-MM-DD HH:MM:SS -----, local none
kernel log [ 12345.678901] seconds since boot boot_rtc_ms + s×1000 → UTC → + utc_offset_s
batterystats history offsets from RESET:TIME: (UTC ms) → UTC → + utc_offset_s

Offset derivation, in order (recorded in index.clock.source):

  1. alarm — dumpsys alarm prints nowRTC=<UTC ms> and nowELAPSED=<ms> together. boot_rtc_ms = nowRTC − nowELAPSED; utc_offset_s = the difference between the dumpstate header's local timestamp and the UTC time of the same instant (header time ≈ alarm dump time within the report's capture window), rounded to the nearest 15 minutes.
  2. timezone — persist.sys.timezone from the properties section, resolved with stdlib zoneinfo at captured_local. Where zoneinfo has no data (some Windows Pythons lack tzdata), the step is skipped.
  3. none — kernel and batterystats events keep elapsed time only and carry "clock": "elapsed" in their row; timeline says so on stderr. Nothing is guessed.

--since grammar. HH:MM[:SS], MM-DD HH:MM[:SS], YYYY-MM-DD HH:MM[:SS], or relative -30m / -2h (back from captured_local). --window is a duration 90s / 5m / 1h, default 5m; the window is [since, since + window).

Date selection on multi-day reports. A time with no date resolves against the span the report's logs actually cover (earliest to latest normalised timestamp across the merged sources). If that clock time falls on exactly one date in the span, that date is used. If it falls on more than one (persistent logd, long LAST LOGCAT), the command exits 2 and lists the candidates:

✗ --since 14:15 is ambiguous: the logs cover 2026-11-01 09:02 … 2026-11-03 14:22
  candidates: 2026-11-01 14:15, 2026-11-02 14:15, 2026-11-03 14:15
  pass a date, e.g. --since "2026-11-03 14:15"

A time outside the span is exit 1 ("no events in window"), with the span printed. A local time inside a DST fold resolves to its first occurrence and the output says so.

§5.6Output, JSON schema and exit codes

Envelope. Every command writes one JSON document to stdout; progress and errors go to stderr via _console.py. --json is accepted on every script for canon parity and silences stderr progress. Default output is capped at 4096 bytes (2048 for query … sample and locate, per the fallback criterion); when the cap bites, whole rows are dropped from the end of the ranked list — never bytes — and the document stays valid JSON:

{"schema": "bugreport.query.sections/1", "truncated": true, "shown": 61, "omitted": 781,
 "total": 842, "full": "rerun with --limit 0 or --output FILE", "rows": [ … ]}

truncated is always present (false when nothing was dropped), so callers branch on one key. --limit N caps rows; --limit 0 removes both the row and the byte cap; --output FILE writes the full, uncapped document to a file and prints only a one-line summary envelope to stdout. Redaction (§ 5.10) applies to every one of those paths unless --no-redact is given.

analyze_bugreport.py schema (bugreport.analyze/1; a major bump on any removed or renamed field, a minor 1.x never needed since additions are backward compatible and the string carries only the major):

Finding fields: id (stable, <family-slug>.<problem>), family (F1–F11), severity (critical · high · medium · low · info), score (0–1, orders findings within a severity), claim (one line, ≤ 160 chars, redacted), facts (numbers and short strings — the measured values the claim rests on), subjects (packages/processes with a role of cause · victim · holder), evidence (≥ 1 pointer: section + byte offset, or an FS/ path), advice_id, detector. --advice adds advice (the canned one-line remedy). Ranking: severity, then score, then id. Family views (--family memory etc.) add a views.<slug> table capped the same way. report never carries the serial number or any account.

Exit codes (all five scripts):

Code Meaning
0 Ran and produced its document — including "no findings" and "no matches"
1 The data is unusable for the request: not a bugreport, no main entry in the zip, nothing in the --since window, schema mismatch in compare
2 Usage or internal error: bad flag, ambiguous --section or --since, unwritable --output, unexpected exception

§5.8Detector contract

@detector(
    id="memory.pressure",                  # unique; prefix = family slug
    family="F6",
    inputs=("meminfo", "procstats", "SYSTEM LOG", "PSI"),  # section names it reads
    findings={"memory.swap_thrashing": "memory.free-ram",  # finding id -> advice_id
              "memory.background_hog": "memory.restrict-app"},
)
def detect(ctx: Context) -> Iterable[Finding]: ...
  • Family slugs (for --family and id prefixes): F1 battery, F2 thermal, F3 reboots, F4 anr, F5 crashes, F6 memory (also churn, a view whose detectors are F6), F7 network, F8 peripherals (Bluetooth, GPS, sensors), F9 storage, F10 security, F11 battery-health.
  • Inputs are read only through ctx.section(name) -> Slice | None and ctx.fs(glob) -> Iterator[Member]; a detector never opens the file itself, so every read is a bounded slice.
  • Fail soft. A missing input returns no findings and records absent; an input whose layout the detector does not recognise raises NotParsed(section, reason); any other exception is caught by the run loop. Both land in not_parsed with a route naming the query command to use instead. The run never dies on one detector. Unexpected exceptions carry reason: "error: <ExceptionType>", and the fixture suite asserts that count is zero — that is how "zero unhandled exceptions" stays testable while the run stays fail-soft.
  • Deterministic. Same input → same findings, same order, byte-identical JSON (apart from redaction tokens, which are salted per run).
  • Tested both ways. Each detector has one fixture scenario that fires it and one that does not (spec success criterion, family coverage).
  • The registry is the single source of finding ids and their advice_ids; references/detectors.md is generated from it.

§5.9Advice reference

references/advice.md holds one entry per advice_id, headed ### <advice_id>. Each entry: a first line that is the canned one-sentence remedy (--advice reads exactly that line, so there is one source), then what to do, the Settings path per Android version where it differs (≤ 3 variants), and when to escalate to repair/support. Several finding ids may share one advice_id. A test diffs the registry's advice_id set against the headings: a missing entry or an orphan heading fails the build. If the file passes the 10K-token reference cap, it splits by family into advice-<slug>.md behind references/_index.md, with the same test reading all of them.

§5.10Redaction

One filter (_redact.py), on by default for every string a script emits — claims, excerpts, show/sample/timeline lines, create_bugreport.py output. Numeric facts are computed before redaction and are not identifiers. Each match becomes <kind:xxxxxxxx>, eight hex characters of an HMAC-SHA256 of the value under a per-run salt that is never stored — the har rule: equal values stay equal within one output, nothing links across two.

Kind Rule
email [A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}
imei 15 digits passing Luhn, bare or keyed (imei, mImei, deviceId); MEID: 14 hex digits when keyed (meid)
imsi 14–15 digits with an MCC prefix (2xx–7xx) when keyed (imsi, subscriberId)
iccid 19–20 digits starting 89, Luhn-valid, bare or keyed (iccid, mIccId)
phone E.164 \+[1-9]\d{7,14}; keyed national forms (mLine1Number, phoneNumber, number=)
mac ([0-9A-Fa-f]{2}[:-]){5}[0-9A-Fa-f]{2}, except all-zero, broadcast and Android's masked 02:00:00:00:00:00
ssid quoted or keyed values in Wi-Fi contexts (SSID: "…", SSID=…, ssid=…, WifiConfiguration … SSID)
account Account {name=…, type=…} and name=… in account sections — name redacted, type kept
coord latitude/longitude pairs with ≥ 3 decimals in location contexts (Location[gps 41.381,2.173 …], lat=…, lon=…)
serial ro.serialno, ro.boot.serialno values (added: same class of identifier)

Known-value harvest. Before output, the filter reads a fixed short list of sections (iphonesubinfo, telephony.registry, account, the properties section) for this device's own IMEI, IMSI, ICCID, line number, serial and account names, and adds them as exact-match terms — catching an unkeyed national phone number or IMSI the patterns alone would miss. The harvested set lives in memory only; it is never written to the cache or any output.

Bare Luhn-valid 15-digit runs may over-redact an unrelated number in an excerpt; that is accepted — an over-redacted excerpt costs a --no-redact rerun, an under-redacted one leaks.

§5.11Synthetic fixture generator

D-9 is the rule: no real report, and no excerpt of one, is ever committed.

  • plugins/core/tests/bugreport/make_fixture.py, stdlib only: build(layout, scenarios, *, seed, target_mb=None, container="txt") -> Path, also a CLI for the benchmark. Output is byte-identical for the same arguments (asserted by hashing two builds).
  • Committed seeds ≤ 200 KB total (seeds/*.tmpl): synthetic section bodies written from what the corpus taught (field names, layouts, number formats), never copied text.
  • Layouts reproduced from spec § 2.1.1: pre-p (no priority blocks, no format-version line), modern (9–17, CRITICAL/HIGH, header ~43 lines before the format line), samsung (+ DUMPSYS NORMAL, AP RESET INFO EXTEND, SEC_MEDIA, End of OLOG), xiaomi (POWERUP_REASON, qsee_log, PERFLOCK HISTORY), oneplus (OMMSERVICE), huawei (kernel live-patch), android9 (QTAGUID). Containers: txt; zip with main_entry.txt and FS/; zip without main_entry.txt with the main file named dumpstate-<date>.txt, dumpstate.txt or example.txt; text-only zip.
  • Traps as switches on any layout: bare \r, UTF-16LE with BOM, NUL and invalid UTF-8 in logcat, locale decimal commas (1,9GB, 0,00), unsampled PSS triples, a timed-out section, a service dumped in two priority blocks.
  • Scenarios are composable signal blocks, one per detector branch (fire and no-fire), including the provenance scenario thrashing (swap ≥ 95 %, kswapd CPU, PSI io, two input-dispatch ANRs) and battery-exhaustion (shutdown,battery, one app foreground with the screen off).
  • PII canaries from reserved ranges only (example.com addresses, +1-555-01xx numbers, RFC 7042 documentation MACs 00:00:5e:00:53:xx, test-TAC IMEIs, invented SSIDs), one of each § 5.10 kind, so pii_in_default_output == 0 has something to find.
  • Scale mode (target_mb) pads with synthetic sections in the provenance size distribution (Wi-Fi HAL, checkin batterystats, activity, package…) for the benchmark; never committed.

§5.12Section registration and packaging

  • metadata.section: android in the SKILL.md frontmatter; a blurb added to SECTION_BLURBS in scripts/sync_sections.py; make sync-sections regenerates assets/sections.json (CI's sync-sections-check fails on drift). No entry in init.py's _SECTION_DEFAULTS is needed for default-off — an unlisted shipped section is off — but --profile all must be checked to include it, as extract is.
  • Release: one minor bump of .bundle-version, a CHANGELOG.md entry, and make sync-version, in the last PR of the stack (see the plan for how that meets CI's version bump job).
